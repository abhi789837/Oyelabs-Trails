# v4.2 decisions

## D1. No Oyelabs process material was provided; the handbook is the place to add it
- **Decision:** `docs/oyelabs-process/` is missing. All handbook entries are seeded with
  industry-standard meanings, status "industry standard – to confirm", and an Oyelabs-meaning field
  that says what to confirm. Typical values are labelled "typical". No Oyelabs policy, price,
  percentage or duration is invented.
- **Why:** the brief's fallback. The handbook is admin-editable and is the single source the
  courses, glossary, tooltips and questions read, so confirming an entry fixes it everywhere.

## D2. The academy lives on the PM trail as five courses (catalog skills) and 44 camps
- **Decision:** courses A–E are catalog skills (`pm-proc-*`) whose content modules are `pmp-*` camps
  on the existing `pm` trail, ahead of the v4.1 agency courses. The plan is in `PLAN.md`.
- **Why:** paths, certificates and the Setup sliders already work per skill and per trail, so a new
  trail id would add plumbing for no learner benefit.

## D3. Handbook template files are generated with `docx` and `exceljs`
- **Decision:** until an admin uploads Oyelabs' own file, each template's default DOCX/XLSX is
  generated on request from the handbook entry with the `docx` (MIT) and `exceljs` (MIT) npm
  packages: brand blue `#2067D3`, the title "Oyelabs — <template name>", the sections as headings
  (docx) or the header row (xlsx), the `example` rows in the "filled" variant, and the footer
  "Generated by Oyelearn. Replace with Oyelabs' own version in Admin → Handbook." Uploads are
  stored under `DATA_DIR/handbook/` and always win over the generated file.
- **Why:** both are pure JavaScript, MIT-licensed and widely used, so there is no native build, no
  external converter and no licence question. Generating from the entry means an admin's edit to a
  template's sections shows up in the download at once. Both stay external to the server bundle.

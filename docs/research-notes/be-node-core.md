## Facts verified
- Threadpool: default 4, max 1024 (libuv threadpool docs), used by fs, `dns.lookup()`, async crypto, zlib; `dns.resolve*()` never uses it; setting `process.env.UV_THREADPOOL_SIZE` at runtime "is not guaranteed to work" (v24 `cli.md`). Demonstrated locally: 6 `pbkdf2` calls finish 4 + 2 by default, all 6 together with `UV_THREADPOOL_SIZE=6`.
- Event loop: phases and the libuv 1.45 / Node 20 timer change quoted from nodejs.org/learn "The Node.js Event Loop"; setImmediate vs setTimeout race in main module (13/2 split over 15 runs) and deterministic inside I/O callbacks (10/10). Every ordering snippet in the quiz was run verbatim on Node v24.11.1, including the ESM flip (`promise` before `nextTick` in `.mjs`) and `nextTick` starvation (process killed by timeout, nothing printed).
- Modules: `require(esm)` unflagged in 20.19/22.12/23, no warning since 22.13/23.5, "no longer experimental" in v24.15.0; `ERR_REQUIRE_ASYNC_MODULE` for TLA (v24 `modules.md` + local run). Prefix-only built-ins `node:sea`, `node:sqlite`, `node:test`, `node:test/reporters` (`require("test")` → `MODULE_NOT_FOUND` locally). `import.meta.dirname` no longer experimental in v24.0.0. Syntax detection on by default since 22.7/20.19. JSON import without `with { type: "json" }` → `ERR_IMPORT_ATTRIBUTE_MISSING`.
- EventEmitter (local runs): removal during emit still calls the listener; additions wait; `off` removes the most recent duplicate; `once` removed before invocation; unhandled `error` throws (non-Error → `ERR_UNHANDLED_ERROR`); `MaxListenersExceededWarning` on the 11th listener; `defaultMaxListeners` 10. The challenge's 13 scenarios were generated by running the driver against Node's real `EventEmitter` (message for non-Error values adapted to the challenge contract).
- Streams: default `highWaterMark` 64 KiB for byte streams (16 KiB on Windows, confirmed locally as 16384), 16 objects in object mode, changed in v22.0.0 (v24 `stream.md`); `write()` returns false once the buffer reaches the threshold; `.pipe()` doesn't close the destination on source error vs `pipeline()` destroying all streams (docs + local run). `fs.createReadStream` hwm 64 KiB.
- http (v24 `http.md` + local): keepAliveTimeout 5000, headersTimeout min(60000, requestTimeout), requestTimeout 300000, maxHeaderSize 16384, chunked encoding without Content-Length, `ERR_HTTP_HEADERS_SENT` from `setHeader` after responding, `server.close()` closes idle connections since v19.
- child_process: `exec` maxBuffer default `1024 * 1024`, shell `/bin/sh` / ComSpec; fork IPC `serialization` default `'json'`; cluster `SCHED_RR` default everywhere except Windows.
- Debugging: `--inspect` default 127.0.0.1:9229, `--inspect-wait`, public-bind warning, `SIGUSR1` reserved to start the debugger, `--watch` stable since v22.0.0, `--cpu-prof`, `--heapsnapshot-near-heap-limit`, `--enable-source-maps` (all present in `node --help` on v24.11.1).
- npm: `npm ci` never writes package.json or lockfiles and removes an existing node_modules; a dependency's package-lock.json is never published and is ignored outside the root project (npm v11 docs). Semver challenge expectations checked against npm's bundled `semver` package (20/20 tests, plus 50k fuzzed in-contract inputs); the path challenge was fuzzed against `path.posix.normalize` (200k inputs, 0 mismatches).

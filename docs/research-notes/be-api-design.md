## Facts verified
- RFC 9110: GET, HEAD, OPTIONS and TRACE are safe; PUT, DELETE and the safe methods are idempotent; 401 requires `WWW-Authenticate`; a server may answer 404 to hide a forbidden resource; 202 is "intentionally noncommittal". RFC 5789: PATCH is neither safe nor idempotent. RFC 6585 defines 428. RFC 9457 obsoletes RFC 7807 and uses `application/problem+json`. RFC 9745 (March 2025) defines the `Deprecation` header and the `deprecation` link relation; RFC 8594 defines `Sunset`.
- Google AIP-180: enum values may be added, but response enums expected to grow should say so because user code may not handle new values; request-only enums are freely extensible (quiz explanation worded to match).
- Stripe versioning blog: backward-incompatible changes live in "version change modules" applied backwards from the current version.
- Stripe idempotency docs: saves the first result's status and body "including 500 errors", keys up to 255 characters, prunable after at least 24 hours, parameters compared with the original, nothing saved when validation fails or a concurrent request conflicts. IETF draft -07: 400 for a missing key, 422 for a reused key with a different payload, 409 while the original is still processing. The challenge follows these.
- Stripe webhooks docs: retries for up to three days with exponential backoff in live mode; no ordering guarantee; duplicates possible, dedupe by event ID; raw body required; signed timestamp with a 5-minute default tolerance; "Don't use a tolerance value of 0", which disables the recency check; one signature per active secret during rotation.
- Standard Webhooks spec: `webhook-id`, `webhook-timestamp`, `webhook-signature` headers; signs `msg_id.timestamp.payload`; `v1,<base64>` signatures, space-delimited for rotation; constant-time comparison; timestamp tolerance. GitHub: `X-Hub-Signature-256: sha256=<hex HMAC>`, compare with `timingSafeEqual`.
- JSON re-serialization claims in the webhook quiz were run on Node 24: `JSON.stringify(JSON.parse('{"b":1,"2":2,"x":1.0,"e":"é"}'))` gives `{"2":2,"b":1,"x":1,"e":"é"}`.
- OpenAPI 3.2 (OAI announcement, 23 Sep 2025): Tag Object `summary`/`parent`/`kind`, `query` method, `additionalOperations`, `querystring` parameter location (can't be combined with `in: query`), streaming media types with `itemSchema`, OAuth 2.0 device flow, `oauth2MetadataUrl`. 3.1 uses JSON Schema 2020-12 (no `nullable`) and added top-level `webhooks`. The 3.2 spec: `operationId` must be unique; header parameters named `Accept`, `Content-Type` or `Authorization` are ignored.
- GraphQL spec (September 2025): OneOf input objects (`@oneOf`), schema coordinates. graphql.org Security page: trusted documents can't protect public APIs; depth, breadth, alias and batch limits; query complexity analysis. graphql.org file-uploads page: multipart requests are CORS-simple and need CSRF protection. Apollo APQ: SHA-256 hash, a not-found error, then a retry with the full query, and GET for CDN caching.
- GitHub GraphQL rate limits: points per query, 5,000 points per hour for users, plus node limits.
- DataLoader README: batches loads made within one tick, per-request instances recommended, the batch function must return an array of the same length and order as the keys, per-key `Error` values are cached while failed batches aren't.
- Challenge swap: be-sql's `sql-n-plus-one` topic already has a full DataLoader-batcher challenge (batching, dedupe, `maxBatchSize`, uncached failures). To avoid duplicating it, `api-graphql-resolvers-dataloader` uses a GraphQL-specific challenge instead: validate an operation against a schema and compute depth, naive resolver calls (the N+1 count) and DataLoader batches, with fragments, cycles, aliases and page-size rules.
